# 결과 검증

## 공통

결과를 직접 보고 고친다. 문서 항목 수나 자의적 점수를 품질 증거로 삼지 않는다.

| 관점 | 확인 질문 | 증거 |
|---|---|---|
| 의도 | 좋아한 레퍼런스 특징이 남았는가 | 나란히 비교 |
| 새로운 설계 | 바뀐 구조·기능이 목적에 맞는가 | 대안·선택 이유 |
| 실용성 | 핵심 과업을 끝낼 수 있는가 | 시연·시험 |
| 구현·제작 | 메커니즘을 설명하고 만들 수 있는가 | 코드 실행·모델·공정 조건 |
| 일관성 | 시안·원본·사양이 일치하는가 | 상태·치수·부품 대조 |

`항목 / 방법·조건 / 실제 결과 / 증거 경로 / 수정 / 남은 제약`을 기록한다. 실행하지 못한 것은 미검증으로 적고 다음 확인을 연결한다.

## 웹·앱

실제 프로토타입에서 핵심 과업을 수행한다. 필요한 초기·성공·실패·복구를 확인한다. 읽는 순서·주 행동·입력 보존·뒤로 가기·좁은 폭 잘림을 본다.

키보드·모달 포커스·대비·확대·긴 한국어/빈 데이터·로딩 중 중복 클릭 등 해당 변경에 중요한 조건을 확인한다. 자동 검사만으로 전체 접근성이나 스크린리더를 검증했다고 하지 않는다.

스크린샷은 브라우저·폭·상태를 기록하고 원본 크기로 연다. 레퍼런스와의 차이가 의도한 조정이면 이유를 설명한다. 모바일 확인을 데스크톱 이미지 축소로 대체하지 않는다.

의미 있는 구현에는 적절한 빌드·검사와 핵심 상호작용 테스트를 수행한다. CSS 값 존재 여부만 검사하는 테스트를 늘리지 않는다. 시각 수정은 실제 화면 확인이 우선이다.

## 실물

전체/부품 치수·내부 공간·도면/BOM/뷰 정합성을 확인한다. 움직임의 시작/끝·간섭·조립 접근·지지/하중 경로를 검토한다.

CAD가 있으면 실제 생성·내보내기·재열기를 확인한다. 메시 닫힘·비다양체·치수·단위 등은 가능한 도구로 검사하고 범위를 기록한다. 소스 작성만으로 검사를 수행했다고 하지 않는다.

시제품 시험은 가설과 성공 조건을 먼저 적는다. 예: 예상 하중에서 전도 여부, 실제 손에서 조작 여유, 체결 반복 후 유격. 측정하지 않은 수치를 채우지 않는다.

## 스킬 변경 시 점검할 시나리오

아래는 판단 점검용이며 자동 테스트나 실제 제품 시험 결과가 아니다.

- 사진과 예약 앱 요청: 분야 선택을 반복하지 않고 사진을 열어 비례·색을 추출한다. 예약 완료·변경 흐름을 설계한다.
- 조약돌 느낌 스피커, 크기·예산 미정: 외형 대안과 가정 치수를 제안한다. 부품·음향·조립 미확정을 구분한다.
- 화려한 유리 UI 요청: 취향을 유지하며 대비·저성능·reduced-motion을 해결한다.
- 기존 버튼 크기 수정: 현재 컴포넌트를 확인하고 해당 범위만 수정·화면 검증한다.
- 사진으로 정확한 STEP 요청, CAD 없음: 알 수 없는 치수를 설명하고 치수 초안·편집 소스를 만든다. 미실행 STEP을 제공했다고 하지 않는다.
- 가구와 제어 앱 요청: 물리 조작·앱 상태·연결 끊김을 연결한다. 사진만으로 하중 성능을 확정하지 않는다.
- 기존 철재 프레임과 새 금형 금지 조건의 의자: 다음 이미지 전에 유지할 프레임과 변경할 폼·원단을 구분한다. 프레임 실측 없이 줄어든 외곽의 호환을 확정하지 않는다.
- 치약 용량과 교체 헤드가 추가된 칫솔: 내부 유효 공간·여유·노즐·잠금·분리 경로를 먼저 정리한다. CAD가 실행되지 않았다면 mL나 사용 횟수를 확정하지 않는다.
- CAD 없는 환경의 정확한 용량 요청: 내부 형상과 필요한 가정을 정리하고 계산 가능한 경로를 제시하되 미실행을 명시한다. 가짜 STEP·정밀 도면을 만들지 않는다.
- 스타일만 빠르게 보고 싶다는 요청: 필요한 가정을 적고 외형 시안을 제공한다. 회색 모델이나 반복 승인 없이도 현재 요청을 처리하고 제작 검증과 구분한다.

최종 답변은 결과 링크·추천 이유·실제 확인·중요한 미확인만 간결하게 담는다. 모든 작업에 장문의 검사표를 사용자에게 요구하지 않는다.
